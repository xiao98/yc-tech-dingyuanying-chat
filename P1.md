### Upstream baseline (`npm test`)

`npm test` runs 4 workspaces in series (`test:api → test:packages:api → test:packages:data-provider → test:packages:data-schemas`). Results on this Win 11 + PowerShell host:

| Workspace | Result | Root cause |
|---|---|---|
| `api` | EXIT 3 — 5 FAIL suites | Tests assume Redis on `127.0.0.1:6379`; not running here. `ECONNREFUSED 6379` cascades to "Max reconnection attempts reached" → uncaught process exit. |
| `packages/api` | EXIT 1 — multiple FAIL suites | Same Redis dep + mongodb-memory-server teardown race ("trying to import a file after the Jest environment has been torn down"). |
| `packages/data-provider` | **EXIT 0 — 1066 / 1067 pass, 1 skipped, 0 fail** | Pure-TS unit tests, no infra needed. |
| `packages/data-schemas` | EXIT 1 — 28 / 37 suites fail (1142 / 1446 tests fail) | mongodb-memory-server: first run hit MD5 mismatch (`Md5CheckFailedError`) on the cached binary download; after re-download mongod *does* start, but parallel tests then hit the teardown ordering bug. |

**These are pre-existing upstream issues**, not introduced by P1:
- The fork's HEAD (commit `1bc2692a1`) ships test suites that hard-depend on a running Redis instance.
- `mongodb-memory-server` downloads ~1.1 GB Mongo binary on first run; on this network the initial download was truncated → MD5 fail. Re-download fixed that, but the per-test teardown ordering still races on Windows.
- I did not modify any upstream test or its config (per守则: "不要改原仓库 lint 配置去让 lint 通过，只 fix 你新增代码"). The 21 P1-specific tests run **independently** of Redis/Mongo and pass cleanly.

To get `npm test` to exit 0 against the upstream suite, P2 would need: (a) Redis running locally, (b) mongodb-memory-server binary pre-downloaded and verified, (c) probably patches to upstream test teardown for Windows. All out of P1 scope.
